# Empire Earth in the browser

## Objective
Make Empire Earth (2001, Stainless Steel Studios, incl. The Art of Conquest) playable in a web browser via WebAssembly, using game files supplied by the user (never redistributed).

## Problem / why
No reimplementation or public decompilation of the Titan engine exists. Recent browser ports (Halo CE: decompilation -> WASM; StarCraft: OpenBW reimplementation -> WASI WASM; BO1 Zombies: Three.js reconstruction over extracted assets) show the viable patterns. Empire Earth has none of the prerequisites yet.

## Reference architecture (from heiner/openbw StarCraft web port)
- C++ engine compiled with WASI SDK (reactor model: JS calls init/step/render), no SDL.
- Rendering and UI in JS on a canvas; multiplayer via WebRTC copy-paste invite.
- Game data loaded client-side. Our legal model: user supplies files -> stored in OPFS.

## Scope (phase 0: discovery)
- Community reverse-engineering inventory (EnergyCube / NeoEE / EE-modders).
- Obtain GOG offline installer, extract with innoextract, inventory file formats.
- Analyze the executable (size, compiler, DirectX/DirectPlay imports, protection).
- Decide route: decompilation (faithful) vs reconstruction (visible sooner).

## Constraints
- Never commit or host game assets or binaries. Game files live outside the repo (`~/Games/EmpireEarth`).
- Legal copy only (GOG Gold Edition).

### Assessment (input for T6)
Decompilation is far more tractable than assumed: unpacked MSVC 6 binaries, engine API fully named (4432 symbols), game classes named via RTTI, source tree layout known, and a plugin architecture (renderer, transport) that can be swapped module by module. Main cost: ~4.3 MB of unnamed game-logic code in the exe. Suggested route: incremental decompilation verified against the original (replace functions/modules while the original still runs under Wine, OpenRCT2-style), then compile the full C++ to WASM with WebGL and WebRTC replacements for the renderer and transport plugins.

## Phase 1 — First decompiled module: `TCP Protocol.dll`

### Why this module
Smallest plugin (37 KB, 4 sections). Pure C ABI: 30 `NPIM*` + 3 `PIM*` exports, resolved by the engine's `PIMModule::GetEntry` (GetProcAddress by name). Imports only MSVCRT, WS2_32, iphlpapi, kernel32, sxlrt233 and 39 engine symbols. A drop-in replacement proves the whole loop (decompile → clean C → differential test → in-game) without MSVC C++ ABI work. The renderer (`DX7HRTnLDisplay.dll`) exports MSVC-mangled C++ classes and comes later.

### Method
1. Ghidra headless decompiles the original module. Raw decompiler output stays outside git (`~/Games/EmpireEarth-re/`).
2. Clean C reimplementation in `src/plugins/tcp_protocol/` exporting the same symbols.
3. Differential test harness (Win32 console exe run under Wine): loads a protocol DLL by path and checks behavior; the original DLL is the oracle, ours must match.
4. Drop-in test in a working copy of the game under Wine.

### Contract (evidence: LLE `GEInitialize` 0x1004a2cc → `PIMModule::GetModule` 0x100575d2)
- Engine-facing surface is 4 plain C exports: `PIMGetName`, `PIMGetType` (must return `'rast'` 0x72617374), `PIMIsValid` (activates, checks screens, deactivates), `RPIMGetRasterizer` (returns a static `DX7TnLRasterizer`, "Direct3D Hardware TnL"). The other 251 mangled exports are unused class-export side effects (no exe/LLE references).
- Everything else crosses through positional vtables: GERasterizer 78 slots (DX7Rasterizer extends to 82), GEScreen 20, GESurface 32, GEMovie 8, GEVertexArray 16, GEPolygonArray 10. The plugin also reads private fields of ~12 engine classes (GEModel, GEMaterial, GETerrainMesh, GETexture, GELight…) inline.
- Selected by config `"Rasterizer Name"="Direct3D Hardware TnL"` in the Wine prefix, so TnL is the oracle. Non-TnL is the same source plus 4 differing vtable slots.
- D3D7 usage is narrow: one FVF `0x152` (36-byte vertex), one ring vertex buffer per screen (2442 vertices), indexed triangle/line lists, fixed-function lighting and linear vertex fog, texture stage 0 only, textures are DDraw surfaces (12 formats incl. DXT1), GDI text on a surface DC, Bink to a locked surface (3 intro movies only). Heaviest: `TransformToCamera` (CPU, float-sensitive), terrain draw.

### Recommended route
Clean C++ clone built with clang `--target=i686-pc-windows-msvc` (MSVC vtable layout, mangling and overload slot order confirmed by a compile-only probe; link via `lld-link` not yet proven; fallback: hand-written C vtables under mingw). Front-end written against a `Dx7Device` seam: prove it trace-identical on real D3D7 under Wine, then swap in a WebGL2 backend. ### Hard for the browser (with evidence)
1. **Real concurrency with kHz polling.** 13 game threads (5 at TIME_CRITICAL) coordinate with 100 k SetEvent, 83 k WaitForSingleObject, 130 k PeekMessageA, 106 k Sleep and 141 k timeGetTime in 57 s (2-3 k/s each). Needs either SharedArrayBuffer workers with Atomics (cross-origin isolation) or a deterministic green-thread scheduler inside the emulator with sub-millisecond switching; thread priorities can be dropped, and no Suspend/Terminate is needed.
2. **x87 control word.** `_controlfp` 313,961 calls (313,882 are `(0,0)` reads, 78 set 53-bit precision, 1 sets 24-bit) at about 5.5 k/s from the engine loops: the emulated FPU must model precision control exactly and make the read path cheap.
3. **GDI text layout on the critical path.** 41 k ExtTextOutA, 55 k GetTextExtentPoint32A (13.8 k from LLE itself, so layout is game-visible), 110 k SelectObject, 82 k colour/mode calls, 42 fonts from 5 Windows faces. Needs a GDI text subsystem with metric-compatible fonts (Arimo/Tinos/Cousine for Arial/Times/Courier; Tahoma has no free metric twin). Moves into our code when the renderer plugin is replaced, but the measure calls stay.
4. **163 MB archive via file mapping plus tiny reads.** 3 whole-file `MapViewOfFile` and 56 k ReadFile calls averaging 8.7 bytes, plus complete reads of three of its own DLLs; needs OPFS/IndexedDB-backed mapping with cheap small reads and a memory budget that holds the mapping and the heap.
5. **PE loader semantics.** Dynamic loading of 11 game binaries with repeated load/free cycles (Default.dll x4), `LOAD_WITH_ALTERED_SEARCH_PATH`, plugin discovery by directory scan and `GetProcAddress` by mangled C++ names, 35 Miles provider DLLs loaded twice, 1,892 TLS callbacks, DllMain ordering on unload. The providers can be refused (only the `.asi` codecs matter), the loader cannot be skipped.
6. **Music and sound stack.** DirectMusic (Performance, Loader, one more CLSID created by LLE; Wine adds dmime/dmusic/dmsynth/dmloader/dmcompos with 3 TIME_CRITICAL threads and DLS synthesis) and DirectSound with a mixer thread at about 310 wakeups/s and 550 buffer writes per minute. No browser equivalent exists for DirectMusic; it needs a reimplementation (segments, styles, DLS) or an alternative music path; DirectSound maps to an AudioWorklet.
7. **Window, message and input model.** Per-thread message queues (`PostThreadMessageA`), 3 windows and a call-wnd-proc hook, WM_PAINT at 480/s, a 50 ms `SetTimer`, IME context calls, and DirectInput 7 with exclusive buffered mouse plus non-exclusive keyboard polled at about 1 kHz: needs Pointer Lock, a low-latency event queue and a faithful message pump.
8. **Small, easy parts that still must exist.** Registry (about 80 values, written back at exit: IndexedDB), 5 Winsock calls from the TCP plugin (WebRTC/WebSocket replacement; LAN broadcast has no browser equivalent), Windows clock (`timeGetTime` 3 k/s, QPC 0.4 k/s: `performance.now()`), `CreateProcess`/`ShellExecute` (dead at the menu).

### Rough sizing of the Win32 layer
- Menu scenario (startup, menu, exit): **about 160 distinct Win32 entry points** are exercised: 135 imported functions called by game modules (kernel32 70, user32 32, gdi32 13, advapi32 5, ws2_32 5, imm32 3, winmm 3, ole32 3, dinput 1) + 16 reached through the compat shim or dynamically (SwitchToThread, CreateWindowExA, LoadLibraryExA, ...) + about 12 hot kernel32 functions (certainly used, untraced). The C runtime is a separate, larger surface (4 traced + about 100 untraced hot functions) that an emulator can take from Wine's own x86 `msvcrt.dll`.
- Upper bound for the whole game: the 372 imported Win32 functions (kernel32 131, user32 82, winmm 43, gdi32 38, wsock32 28, ws2_32 24, advapi32 7, imm32 7, ole32 3, version 3, ddraw 3, dinput/shell32/iphlpapi 1 each) + 167 msvcrt + COM surfaces: DirectInput7 (IDirectInput7/IDirectInputDevice7), DirectSound (IDirectSound, buffers), DirectMusic (about 8 CLSIDs), DirectDraw7/Direct3D7 (the renderer plugin; already planned as a WebGL replacement). 209 of the 372 imports (56%) were never called on the way to the menu (many are gameplay-time: saves, clipboard, network, mixer).
- Where the cost sits: about 100 of the 160 are trivial (sync primitives, time, strings, TLS, heap, handles); about 25 need real design (threads/events, file system and mapping, registry, window/message pump, GDI text, timers, LoadLibrary/GetProcAddress, DirectInput); three families dominate the risk (DirectMusic/DirectSound audio, GDI text, x87 precision). Effort in person-time was not estimated.
- Reproduce or extend: `bash tools/game_run/scripts/runtime-inventory.sh --tag <name> --profile broad|timers|full` (needs the run budget file edited; the three runs are recorded) and `python3 tools/game_run/scripts/ri.py summarize ...` on the kept logs; tests: `make test-game-run` (ri-analyze, ri-driver, ri-close).
